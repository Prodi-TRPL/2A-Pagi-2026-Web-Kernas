TLDR
----
Rebuilding an existing Express.js + Vue.js web app into a Laravel monolith.
Manages distribution of official letters (SK/ST) for Polibatam.
Database and planning are COMPLETE. Now in DEVELOPMENT STAGE.

⚠️  MAJOR CHANGE FROM VERSION 1:
    Authentication no longer uses the external Polibatam API.
    The system now uses its own local database for login credentials.
    This also means normalization has moved from 2NF → 3NF because
    dibuat_oleh and nip_pegawai are now proper FK → pengguna.id
    instead of plain VARCHAR values.

1. THE ORIGINAL APPLICATION (what I am replacing)
════════════════════════════════════════════════════════════════════════

The original app was a student project built with:
  - Frontend : Vue.js + Vuetify (separate repo, deployed on Vercel)
  - Backend  : Express.js + Prisma ORM (separate repo, deployed on Vercel)

WHY I AM REPLACING IT:
  - Two separate codebases too complex to maintain
  - SQLite not suitable for production
  - Employee data stored as JSON blobs — not relational
  - No proper normalization — data redundancy and update anomalies
  - No document numbering system (SK-2026-001 etc.)
  - No version history / audit trail

FEATURES BEING KEPT:
  - Login (now local, not via Polibatam API)
  - Dashboard with document counts and recent activity
  - Grup verifikasi management (was "tag group")
  - Document management — SK and ST official letters
  - Pengajuan submission workflow
  - Admin role management

3. AUTHENTICATION — HOW LOGIN WORKS (V2 — LOCAL AUTH)
════════════════════════════════════════════════════════════════════════

⚠️  NO MORE POLIBATAM API — credentials stored in local pengguna table.

Login flow:
  1. User enters username + password on login page
  2. Laravel checks pengguna table for matching username
  3. Verifies password using bcrypt hash (password_verify / Hash::check)
  4. If valid → stores pengguna data in Laravel session
  5. Middleware checks session on every subsequent request

The pengguna table now stores:
  - nip         (still used as institutional identifier)
  - username    (login credential)
  - password    (bcrypt hashed)
  - nama        (full name — stored locally, not from API)
  - unit        (department — stored locally)
  - jabatan     (position/title — optional)
  - is_admin    (boolean role flag)

Admin creates/manages user accounts via User Management feature.
No self-registration — admin adds users manually.

SESSION DATA stored after login:
  - pengguna.id
  - pengguna.nip
  - pengguna.nama
  - pengguna.unit
  - pengguna.is_admin

4. USER ROLES
════════════════════════════════════════════════════════════════════════

Two roles — is_admin boolean on pengguna table:

  ADMIN (is_admin = 1):
    - Manage pengguna accounts (create, edit, delete, set admin)
    - Create, edit, delete grup_verifikasi
    - Publish dokumen
    - Approve / reject pengajuan
    - Manage template_surat
    - View all documents and pengajuan

  STAFF (is_admin = 0):
    - Submit pengajuan
    - Edit/delete own pengajuan (only when POSTED)
    - View documents they are assigned to

6. DATABASE DESIGN (13 tables, normalized to 3NF)
════════════════════════════════════════════════════════════════════════

Normalization: 3NF (upgraded from 2NF in v1)

Why 3NF now:
  - Data pegawai now stored locally in pengguna table
  - No longer need nip_pegawai VARCHAR in junction tables
  - dibuat_oleh VARCHAR replaced by id_pengguna FK everywhere
  - This eliminates all transitive dependencies
  - pengguna is now the central hub with FK relations to all tables

Key design rules:
  - All IDs: INT UNSIGNED AUTO_INCREMENT (not BIGINT)
  - Timestamps: DATETIME (not TIMESTAMP — avoids year 2038 limit)
  - Date-only fields: DATE
  - Passwords: bcrypt hashed VARCHAR(255)

TABLES:

  1.  pengguna
        id PK, nip UNIQUE, username UNIQUE, password (hashed),
        nama, unit, jabatan, is_admin, created_at, updated_at

  2.  grup_verifikasi
        id PK, id_pengguna FK, nama_grup, is_deleted,
        created_at, updated_at

  3.  anggota_grup_verifikasi
        id PK, id_grup_verifikasi FK, id_pengguna FK,
        created_at
        UNIQUE(id_grup_verifikasi, id_pengguna)

  4.  nomor_dokumen
        id PK, tipe ENUM(SK/ST), tahun YEAR, urutan INT,
        nomor_terformat UNIQUE, created_at

  5.  dokumen
        id PK, id_nomor_dokumen FK, id_pengguna FK, tipe, nama_dokumen,
        tgl_dokumen DATE, filepath, catatan, dari_pengajuan,
        kode_unik UNIQUE, rendered_body LONGTEXT, verified_at,
        is_deleted, created_at, updated_at

  6.  anggota_dokumen
        id PK, id_dokumen FK, id_pengguna FK, created_at
        UNIQUE(id_dokumen, id_pengguna)

  7.  grup_verifikasi_dokumen
        id PK, id_dokumen FK, id_grup_verifikasi FK, created_at

  8.  template_surat
        id PK, id_pengguna FK, tipe ENUM(SK/ST), nama_template,
        filepath, versi INT, is_aktif, created_at, updated_at

  9.  pengajuan
        id PK, id_pengguna FK, id_grup_verifikasi_verifikator FK,
        judul, tipe, status ENUM(POSTED/APPROVED/REJECTED/PUBLISHED),
        daftar_menimbang, daftar_memperhatikan, daftar_memutuskan,
        ada_lampiran, filepath, filepath_lampiran,
        rencana_pengambilan DATE, tgl_terbit DATE, catatan,
        urutan_antrian, nomor_diusulkan,
        is_deleted, created_at, updated_at

  10. anggota_pengajuan
        id PK, id_pengajuan FK, id_pengguna FK, created_at
        UNIQUE(id_pengajuan, id_pengguna)

  11. grup_verifikasi_pengajuan
        id PK, id_pengajuan FK, id_grup_verifikasi FK, created_at

  12. riwayat_pengajuan
        id PK, id_pengajuan FK, id_pengguna FK,
        aksi ENUM(DIBUAT/DIEDIT/DISETUJUI/DITOLAK/DITERBITKAN),
        catatan_aksi, versi INT, snapshot_konten JSON, created_at

  13. log_audit
        id PK, id_pengguna FK, aksi, tipe_model, id_model INT,
        nilai_lama JSON, nilai_baru JSON, created_at
