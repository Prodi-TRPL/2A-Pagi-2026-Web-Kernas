3. AUTHENTICATION — LOCAL AUTH (no external API)
════════════════════════════════════════════════════════════════════════

No Polibatam API. Credentials stored in local pengguna table.

Login flow:
  1. User enters username + password
  2. Laravel checks pengguna table for username
  3. Hash::check($password, $pengguna->password) — bcrypt verify
  4. If valid → store pengguna data in Laravel session
  5. Middleware checks session on every request

pengguna table stores:
  - nip         (institutional identifier — UNIQUE)
  - username    (login credential — UNIQUE)
  - password    (bcrypt hashed VARCHAR(255))
  - nama        (full name)
  - unit        (department)
  - jabatan     (position/title — nullable)
  - is_admin    (boolean role flag)

Admin creates/manages all user accounts. No self-registration.

SESSION stored after login:
  - pengguna.id, nip, nama, unit, is_admin

4. USER ROLES
════════════════════════════════════════════════════════════════════════

  ADMIN (is_admin = 1):
    - Manage pengguna accounts
    - Create/edit/delete grup_verifikasi
    - Review pengajuan (POSTED → REVIEWED) before verifikator sees it
    - Publish dokumen (APPROVED → PUBLISHED)

    - Manage peraturan (add, edit, delete regulations)
    - Manage masukan library (add field types for future dynamic form)

  STAFF (is_admin = 0):
    - Submit pengajuan
    - Select peraturan for "mengingat" section when submitting
    - Edit/delete own pengajuan (only when POSTED)
    - View documents they are assigned to


════════════════════════════════════════════════════════════════════════
5. PENGAJUAN STATUS FLOW
════════════════════════════════════════════════════════════════════════

  POSTED    → Staff submitted. Admin has not reviewed yet.
              Verifikator CANNOT see this yet.

  REVIEWED  → Admin reviewed, fixed typos, approved for verification.
              Verifikator CAN now see and act on this.

  APPROVED  → Verifikator approved the pengajuan.
              System auto-generates .docx borang from template_surat.

  REJECTED  → Verifikator rejected with reason (stored in catatan).
              Staff can edit and resubmit → returns to POSTED.
              urutan_antrian is PRESERVED — does not reset.

  PUBLISHED → Admin uploaded signed document → dokumen entry created.

  Flow:
  POSTED → [Admin review] → REVIEWED → [Verifikator] → APPROVED/REJECTED
  APPROVED → [Admin publish] → PUBLISHED
  REJECTED → [Staff edit] → POSTED (urutan_antrian preserved)


════════════════════════════════════════════════════════════════════════
6. TEMPLATE SURAT — ONLYOFFICE INTEGRATION
════════════════════════════════════════════════════════════════════════

Templates are .docx files stored in Laravel storage.
Admin edits templates using ONLYOFFICE Document Server (Docker).

ONLYOFFICE Docker setup:
  docker run -d -p 80:80 onlyoffice/documentserver

IMPORTANT — template_surat has NO relation to dokumen:
  - Templates only used when generating borang after APPROVED
  - Result stored in pengajuan.filepath
  - dokumen stores the final signed document, NOT the template

Placeholders in templates (replaced when generating borang):
  {{judul}}               — pengajuan.judul
  {{tipe}}                — SK or ST
  {{daftar_menimbang}}    — pengajuan.daftar_menimbang
  {{daftar_memperhatikan}}— pengajuan.daftar_memperhatikan
  {{daftar_memutuskan}}   — pengajuan.daftar_memutuskan
  {{mengingat}}           — auto-generated from pengajuan_peraturan
  {{tgl_terbit}}          — pengajuan.tgl_terbit
  {{nomor}}               — from nomor_dokumen

7. DYNAMIC FORM FOUNDATION (masukan + template_masukan)
════════════════════════════════════════════════════════════════════════

WHY THESE TABLES EXIST:
  Different letter types need different input fields. Instead of
  building separate pages for each letter type, the masukan table
  provides a master library of reusable field definitions that can
  be linked to any template via template_masukan.

CURRENT STATUS:
  These tables are FOUNDATION ONLY — not yet used in the active
  pengajuan workflow. The pengajuan form still uses the fixed fields:
  daftar_menimbang, daftar_memperhatikan, daftar_memutuskan.

  When the time comes to migrate to dynamic forms:
    1. Define field types in masukan table
    2. Link fields to templates via template_masukan
    3. Replace fixed fields in pengajuan with a new junction table
    4. Blade form renders dynamically based on template_masukan

masukan table:
  - id   INT PK
  - nama VARCHAR(100)   — field name e.g. "Tujuan Perjalanan"
  - tipe ENUM(text, textarea, date, number, select)

template_masukan table (junction):
  - id                INT PK
  - id_template_surat INT FK → template_surat
  - id_masukan        INT FK → masukan
  UNIQUE(id_template_surat, id_masukan)

FUTURE MIGRATION PATH (when needed — not now):
  1. Add label, is_required, urutan to template_masukan pivot
  2. Add pengajuan_jawaban table (id_pengajuan FK, id_masukan FK, nilai TEXT)
  3. Remove daftar_menimbang, daftar_memperhatikan, daftar_memutuskan
     from pengajuan table
  4. Update Blade form to render fields dynamically

8. PERATURAN FEATURE
════════════════════════════════════════════════════════════════════════

The peraturan table stores a library of legal regulations that staff
select when filling in the "mengingat" section of a pengajuan form.

peraturan table:
  - kode        VARCHAR(100) UNIQUE — e.g. "UU No. 12 Tahun 2012"
  - judul       VARCHAR(255)
  - jenis       VARCHAR(50)         — e.g. "UU", "PP", "Permendikbud"
  - tahun       YEAR
  - keterangan  TEXT NULL           — optional
  - id_pengguna FK → pengguna

pengajuan_peraturan junction:
  - id_pengajuan FK → pengajuan
  - id_peraturan FK → peraturan

9. DATABASE DESIGN (17 tables, 3NF)
════════════════════════════════════════════════════════════════════════

Normalization: 3NF
  - pengguna is central hub — FK from all tables
  - All IDs: INT UNSIGNED AUTO_INCREMENT
  - Timestamps: DATETIME | Date-only: DATE | Passwords: VARCHAR(255) bcrypt

TABLES:

  1.  pengguna                  — local auth + employee data
  2.  grup_verifikasi           — named verifier groups
  3.  anggota_grup_verifikasi   — group members
  4.  nomor_dokumen             — auto-numbering SK/ST per year
  5.  dokumen                   — published official letters
  6.  anggota_dokumen           — employees assigned to document
  7.  grup_verifikasi_dokumen   — document ↔ group junction
  8.  template_surat            — .docx templates via ONLYOFFICE
  9.  masukan                   — master field library (dynamic form foundation)
  10. template_masukan          — template ↔ masukan junction
  11. peraturan                 — regulations library for "mengingat"
  12. pengajuan                 — submission requests
  13. pengajuan_peraturan       — pengajuan ↔ peraturan junction
  14. anggota_pengajuan         — employees assigned to pengajuan
  15. grup_verifikasi_pengajuan — pengajuan ↔ group junction
  16. riwayat_pengajuan         — version history
  17. log_audit                 — system-wide activity log

KEY ENUM VALUES:
  pengajuan.status:
    POSTED | REVIEWED | APPROVED | REJECTED | PUBLISHED

  riwayat_pengajuan.aksi:
    DIBUAT | DIEDIT | DIREVIU | DISETUJUI | DITOLAK | DITERBITKAN

  masukan.tipe:
    text | textarea | date | number | select
